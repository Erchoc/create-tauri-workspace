What you get

The parts that are tedious to wire up yourself

Signed automatic updates

One command generates the signing key, writes the public key into the configuration, and prints the secrets to upload. GitHub Releases hosts the manifest, so there is no server.

A design system, not a theme

Every colour, radius and spacing value is a token. Light and dark are both defined, and a theme control ships in the window.

Two Rust crates, one boundary

crates/core holds testable logic and never depends on Tauri. crates/app adapts it to the desktop shell. New crates wait for a real reason.

Release workflows that fail fast

A preflight job checks the tag, the version, and the signing secret before any platform starts building. Releases land as drafts for you to review.

Desktop basics, handled

Single-instance launch, restored window position, structured logs, persisted settings, and an error boundary so a rendering failure never leaves a blank window.

Guidance for coding agents

One AGENTS.md, imported by CLAUDE.md, plus a skill that Claude Code and Codex both read.

Quick start

From nothing to a running window

  1. Check the machine

    $ npx create-tauri-workspace doctor

    It reports each tool below, plus the platform webview, and prints the exact command to fix anything missing.

    Tool Minimum Why
    Bun 1.4 Runs every project command
    Node.js 24 Runs the release and updater scripts
    Rust 1.98 Compiles the application

    These bind you, not your users: what you ship is a native binary with no JavaScript runtime inside it.

  2. Generate the project

    $ npx create-tauri-workspace my-app \
    --identifier dev.you.myapp \
    --repo you/my-app

    The identifier is a reverse domain name you control. Without a domain, use io.github.your-handle.my-app.

  3. Run it

    $ cd my-app
$ bun run dev

  4. Turn on automatic updates

    $ bun run updater:init --repo you/my-app

    Back up the private key it reports. It is the only thing that can update copies of the app that are already installed.

  5. Release

    $ bun run release:check
$ git tag app-v0.1.0 && git push origin app-v0.1.0

    macOS, Windows and Linux build in parallel and upload to a draft release.

For coding agents

One skill, read by Claude Code and Codex

Both tools read the same SKILL.md format from different directories. The installer writes to both. 

$ npx create-tauri-workspace skill install          # this project
$ npx create-tauri-workspace skill install --global # every project
Tool Installed to
Claude Code .claude/skills/desktop-app/
Codex .agents/skills/desktop-app/

Claude Code can also install it as a plugin: /plugin marketplace add erchoc/create-tauri-workspace then /plugin install desktop-app@create-tauri-workspace.

After that, asking for a desktop app is enough. The skill knows to pick an identifier, verify the build, keep logic out of command handlers, use the design tokens, and tell you early when something needs a paid account.

Read this before you promise a release date

Three signatures, and only one is free

They are easy to confuse, and confusing them is the most common way a first desktop release goes wrong.

Signature Signs Needed for Cost
Update signature The update package Automatic updates on every platform Free
Apple Developer ID The .app and .dmg macOS opening the app at all Apple Developer Program
Windows code signing The .exe installer Avoiding a SmartScreen warning Certificate authority

Without any signing

macOS tells anyone who downloads your app that it is damaged and refuses to open it. Windows shows a warning users can click through. Linux is unaffected.

Updates need macOS signing too

An update replaces the application bundle. On macOS an unsigned replacement will not launch, so update signing alone is not enough there.

Missing secrets do not break the build

The release workflow skips each signing step whose secret is empty, so a repository without credentials still produces unsigned builds instead of failing.

The full distribution guide lists every secret and where to get it.

FAQ

Honest answers

Do I need a Mac to build the macOS app?
To build it locally, yes. The included release workflow uses GitHub's macOS runner, so you can publish macOS builds without owning one — but you still need an Apple Developer account to sign and notarize them.
How is this different from the official Tauri scaffolder?
create-tauri-app lets you choose every part of the stack and stops there. This one makes those choices and adds the pieces you would otherwise add by hand: the crate boundary, signed updates, a design token system, release preflight, and agent guidance.
Does the app ship Node.js or Bun?
No. Bun is a development tool. A production build embeds the compiled static frontend inside a Rust binary.
Can I still use it without automatic updates?
Yes. Updates are off until you run bun run updater:init. The updater plugin is not even registered without a signing key, so the interface hides the update controls rather than offering an install it cannot verify.
What if I lose the update signing key?
Every installed copy stops accepting updates, and those users have to download a new installer by hand. Back it up when the setup command prints its location.
Is Linux supported?
Yes — AppImage and Debian packages build in CI. macOS and Windows are the primary targets, and Linux comes along for free.
